# Refract Operations

## Deployment modes

For a local desktop-only service, run the release binary with the defaults. It listens on `127.0.0.1:3939`, stores SQLite in `refract.db`, and permits gateway calls without a Refract API key.

For a container or remote listener, Refract requires both controls before binding:

- `REFRACT_REQUIRE_AUTH=true` protects `/v1` and `/v1beta` with Refract API keys.
- A management token protects `/api`. Set it declaratively with `REFRACT_ADMIN_TOKEN` or configure it in the UI before changing from a loopback listener.

`REFRACT_ADMIN_TOKEN` is hashed before persistence and is never logged. When it remains present, every restart resets the management token to that value. This makes container configuration deterministic and also means an in-UI token change will not survive the next restart until the environment is updated.

## Docker Compose

```sh
cp .env.example .env
# Put a long random secret in REFRACT_ADMIN_TOKEN.
docker compose up -d --build
docker compose ps
curl --fail http://127.0.0.1:3939/health/ready
```

The provided Compose service:

- publishes only `127.0.0.1:3939` on the host;
- runs as UID/GID 10001 with `no-new-privileges`;
- uses a read-only root filesystem and a writable `/data` volume;
- initializes and reaps child processes with `init: true`;
- restarts unless explicitly stopped.

Create at least one gateway API key in the UI before configuring clients. The management token and gateway API keys are deliberately separate credentials.

## Health and logs

`GET /health/live` returns 200 while the HTTP process can answer. It does not depend on SQLite.

`GET /health/ready` executes a real SQLite `SELECT 1`. It returns 503 when the database is unavailable and is the correct container or reverse-proxy readiness check.

Application logs go to stdout/stderr. Configure verbosity with `REFRACT_LOG`, for example `info,refract_router=debug`. Request records are stored in SQLite and default to 30 days of retention; the UI can set 1–3650 days. Cleanup runs once at startup and then every 24 hours, reading the latest setting each time.

`GET /metrics` serves Prometheus text-format counters (requests, failures, transcodes, tokens, retries, uptime) collected in-process. Like the health probes it is unauthenticated; restrict it at the reverse proxy if your network requires that. Counters reset on restart, which Prometheus `rate()`/`increase()` handle natively.

### Request tracing

Every gateway response — success or error — carries an `x-refract-request-id` header generated by Refract. The same identifier is stored with the request log, so a client-reported failure can be located with one filter. It is deliberately distinct from `x-request-id`, which upstreams may set themselves and which Refract passes through untouched on native calls.

Log persistence is fire-and-forget: the response returns before the row is committed, so a log line may trail its request by a few milliseconds. This is a deliberate trade — logging never adds latency to the hot path.

## Timeouts and streaming

Two different clocks apply:

- **Non-streaming requests** are bounded by `upstream_timeout_secs` (default 300) end to end.
- **Streaming requests** are exempt from the overall timeout — a long completion may legally run for many minutes. Instead, `stream_idle_timeout_secs` (default 120) bounds the wait for response headers and then the gap between any two frames. A stalled upstream is cut once the idle window elapses; a slow-but-flowing stream is never cut.

When a reverse proxy sits in front, its own idle/read timeouts must exceed `stream_idle_timeout_secs`, otherwise the proxy kills healthy streams before Refract does.

## Circuit breaker

Endpoints that fail consecutively are suspended per `(channel, protocol)` pair. The policy is configurable at runtime under **Settings → 熔断**: failure threshold (0 disables the breaker entirely), base cooldown, and cooldown cap. Cooldowns back off exponentially from the base to the cap; one success fully restores the endpoint. Upstream `Retry-After` headers are honored even below the failure threshold and take precedence when longer than the computed backoff. Breaker state survives restarts and can be reset manually from the channels page. Policy changes apply to subsequent failures immediately without a restart; endpoints already cooling down keep their current deadline.

## Soft quotas

Gateway API keys can carry a token quota (0 = unlimited). Enforcement is **soft**: the check happens at authentication time, and usage is accumulated asynchronously after each request completes. Consequences to be aware of:

- an in-flight request is never interrupted by quota exhaustion;
- the final request against a nearly-exhausted key may overshoot the limit;
- usage counters may lag by a moment because log writing is asynchronous.

For a personal gateway this is the right trade — hard mid-stream cutoffs would waste the tokens already generated. Treat quotas as budget guards, not billing enforcement.

## Graceful shutdown

On SIGTERM/Ctrl-C Refract stops accepting new connections and waits up to `shutdown_grace_secs` (default 30) for in-flight requests — including long streams — to finish, then aborts whatever remains. Raise the window if your workload routinely streams for minutes and you prefer clean completion over fast restarts; container orchestrators must allow at least this long before SIGKILL (Compose `stop_grace_period`, Kubernetes `terminationGracePeriodSeconds`).

## Backup and restore

SQLite may use WAL files, so do not copy only `refract.db` while the service is writing. The simplest consistent Compose backup is a brief stop followed by an archive of the volume:

```sh
docker compose stop refract
docker run --rm \
  -v refract_refract-data:/data:ro \
  -v "$PWD/backups:/backup" \
  alpine:3.22 sh -c 'tar -czf /backup/refract-data.tgz -C /data .'
docker compose start refract
```

Restore into an empty volume while the service is stopped:

```sh
docker compose down
docker volume create refract_refract-data
docker run --rm \
  -v refract_refract-data:/data \
  -v "$PWD/backups:/backup:ro" \
  alpine:3.22 sh -c 'tar -xzf /backup/refract-data.tgz -C /data'
docker compose up -d
```

Keep backups encrypted: the database contains upstream credentials. Refract masks credentials at the HTTP boundary, but the service must retain usable credentials in its database.

### Configuration export/import

For migrating configuration (not logs) between instances, prefer the built-in backup: **Settings → 数据备份** in the UI, or `GET /api/export` / `POST /api/import` with the admin token. The export is a single JSON document containing channels (with plaintext upstream credentials — guard the file like a key), gateway API keys (hash only; original plaintext keys keep working after restore), the routing policy, log retention, and the circuit-breaker policy. Import supports `merge` (skip channels with an existing name, skip known key hashes) and `replace` (wipe channels and keys first; the UI asks for confirmation). The import response lists the names of skipped channels and keys, not just counts. Request logs and live circuit-breaker state are not part of the export; use the volume backup above for full-state recovery.

Feeding a redacted admin `GET /api/channels` response back as a backup is rejected before any data is touched — masked credentials (`sk-a…9f2c`) are not usable configuration.

## Upgrade and rollback

Before upgrading, create a backup. Then rebuild and replace the container:

```sh
docker compose build --pull
docker compose up -d
curl --fail http://127.0.0.1:3939/health/ready
```

Database migrations run when Refract opens the database. To roll back across a schema change, restore the matching pre-upgrade backup together with the previous image; do not run an older binary against a newly migrated database unless that release explicitly documents compatibility.

## Reverse proxy

Terminate TLS at a trusted reverse proxy and preserve streaming semantics: disable response buffering, allow long request durations, and do not compress or coalesce server-sent events. Keep the Refract listener private. The built-in non-loopback guard is a last line of defense, not a substitute for network access controls.
